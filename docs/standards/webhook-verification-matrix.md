## 1. Method

Each provider's inbound contract was verified independently against its own current official documentation; a contract for one provider never answers another. For every row we captured: the inbound surface and the header carrying the signature/secret; the verification algorithm (hash/HMAC family, exactly what bytes are signed, timestamp/nonce and replay window, and whether timing-safe comparison is required); the primary official source; the checked date; and a concise, attributable reason. Where an official docs site renders client-side (SPA), the canonical official URL was rendered and read in full; the cited URL remains the source of truth for re-verification.

Classification values (`SPECIFIED` / `PARTIAL` / `UNRESOLVED`) are defined in §4. Per the evidence contract, a row is only `SPECIFIED` when the official docs **affirmatively** establish every required field; where the docs are **silent** on a required field (e.g. the replay/timestamp window or timing-safe comparison), that silence is a documented gap and the row is at most `PARTIAL`. No provider row was inferred from Plexco's internal design assumptions — the internal tech specs are authority only for **which** provider/surface applies, never for the provider's verification behaviour; where an internal spec conflicts with the official contract, the conflict is flagged, not resolved here.

## 3. Per-provider evidence

### 3.1 SePay — `SPECIFIED`

- **Inbound surface / header:** SePay POSTs bank-transaction events to the merchant's configured webhook URL. The official authentication page documents four methods — None, API Key, HMAC-SHA256, OAuth 2.0. The signature-based method carries `X-SePay-Signature: sha256={hex}` and `X-SePay-Timestamp` (Unix seconds).
- **Algorithm / bytes signed:** HMAC-SHA256 keyed by the configured Secret Key over the exact string `{timestamp}.{raw_body}` (the Unix timestamp, a literal `.`, then the **raw request body bytes**). The docs warn that SePay signs the raw bytes of the body, so re-serializing (`JSON.stringify(req.body)`) breaks the signature — verify against the raw body.
- **Replay window:** reject timestamps off by more than **5 minutes** (±300s) — affirmatively specified.
- **Timing-safe:** required — the docs instruct comparing the reconstructed signature in constant time (`hash_equals`).
- **Alternative documented methods:** API Key = `Authorization: Apikey <key>` (static equality); OAuth 2.0 = `Authorization: Bearer <token>`; None (no header). Plexco's connector spec uses HMAC-SHA256 as the production default with an explicit API-key fallback.
- **Source / checked:** `developer.sepay.vn/en/sepay-webhooks/xac-thuc` (VI: `/vi/sepay-webhooks/xac-thuc`); corroborated by `docs.sepay.vn/tich-hop-webhooks.html`. Checked 2026-07-23.
- **Why `SPECIFIED`:** the official page **affirmatively** fixes every required field — the exact headers, the `{timestamp}.{raw_body}` signed input, the raw-body requirement, the ±5-minute anti-replay window and the constant-time comparison — a fully determined verification contract with no silent field.

### 3.2 ApiPay — `PARTIAL`

- **Inbound surface / header:** ApiPay POSTs events (e.g. `transaction.in`) to the merchant's configured webhook URL; every request carries an `ApiPay-Signature` header.
- **Algorithm / bytes signed:** the official "Webhook Authentication" section provides a Node/Express example that computes `crypto.createHmac("sha256", secretKey).update(payload).digest("hex")` where `payload = JSON.stringify(req.body)` — i.e. HMAC-SHA256 keyed by the webhook secret over the **re-serialized parsed body**, not the raw request bytes. No canonical serialization (key order, whitespace, unicode escaping) is pinned.
- **Replay window:** not documented (silent). **Timing-safe:** yes — the example uses `crypto.timingSafeEqual`. **Format:** hex digest (`.digest("hex")`).
- **⚠ Contract discrepancy — reconcile before implementation:** the official ApiPay contract signs `JSON.stringify(req.body)` (re-serialized parsed JSON), but Plexco's own internal implementation specs mandate HMAC over the **raw** request bytes and explicitly test that re-serialization fails — `feature_connector_onboarding_tech.md:269` (`ApiPay-Signature == HMAC-SHA256(rawBody, webhook_secret)`, §4.5 verifier + unit tests 3–5) and `feature_payment_reconcile_tech.md:322-326`. These two algorithms are **mutually exclusive**: an implementation that follows the internal raw-body spec would reject valid ApiPay callbacks if ApiPay actually signs the re-serialized body (and vice-versa). This evidence does not edit those specs (out of scope) but flags them as **unreconciled/stale on this point**; the exact ApiPay signed representation must be confirmed directly with ApiPay (sandbox capture / support) and the internal specs reconciled to it **before** any ApiPay inbound-webhook code is written. Do not assume raw-body.
- **Source / checked:** `docs.apipay.vn/en/api/webhooks` (VI: `/vi/api/webhooks`); the docs site renders client-side, so the canonical official URL was rendered in full to read the section. Checked 2026-07-23.
- **Why `PARTIAL`:** header, hash family, secret, digest format and constant-time comparison are specified, but the **signed representation is the re-serialized parsed body with no canonical form defined** (so byte-exact reconstruction is not determined), the replay/timestamp window is **silent**, and the documented method **contradicts** Plexco's raw-body implementation specs. The contract is recorded exactly as published and the gaps are flagged rather than resolved by inference.

### 3.3 Zalo Bot — `PARTIAL`

- **Inbound surface / header:** the Zalo Bot Platform (Telegram-style Bot API; API base `bot-api.zaloplatforms.com/bot`) delivers updates via POST to the URL registered with `setWebhook`. Every request carries `X-Bot-Api-Secret-Token` whose value is the `secret_token` configured at `setWebhook`.
- **`secret_token`:** String, required, **8–256 characters**, described as the key used to authenticate requests Zalo sends to your system.
- **Algorithm / verification:** static **secret-token equality** — the receiver compares the header against the configured `secret_token` before processing (official example: `if (secretToken !== WEBHOOK_SECRET_TOKEN) return 403`). There is no HMAC and no body signature by design.
- **Replay window:** not documented (silent). **Timing-safe:** not documented (silent) — the official example uses a plain `!==` comparison.
- **Source / checked:** `bot.zapps.me/docs/webhook/` and `bot.zapps.me/docs/apis/setWebhook/`; both official pages rendered consistently. Checked 2026-07-23.
- **Why `PARTIAL`:** the verification **mechanism** is fully attributable and documented — the `X-Bot-Api-Secret-Token` header, the configured `secret_token`, and the equality check (a bearer-secret-in-header scheme, as with Telegram's Bot API, with no body signature). But the official docs are **silent** on a replay/timestamp window and on whether the comparison must be timing-safe; per the evidence contract, documentation silence is not `SPECIFIED`, so the row is `PARTIAL`. Implementation note: a receiver should still compare in constant time even though the provider does not require it.

### 3.4 Meta Messenger — `PARTIAL`

- **Inbound surface / header:** endpoint registration uses a `GET` verification handshake with `hub.mode=subscribe`, `hub.verify_token` (must match the value configured in the App Dashboard) and `hub.challenge` (echoed back). Event notifications arrive by `POST` with the signature in the `X-Hub-Signature-256` header.
- **Algorithm / bytes signed:** "Generate a SHA256 signature using the payload and your app's App Secret." HMAC-SHA256 keyed by the App Secret over the request payload; the example verifies with `.update(buf)` (the raw request buffer). The docs add an explicit caveat: the signature is generated over an **escaped-unicode** version of the payload with lowercase hex digits (non-ASCII characters are escaped to their `\uXXXX` code-point form — the provider's own example escapes the string `äöå`), so calculating against the decoded bytes yields a different signature; receivers must verify against the exact bytes as delivered.
- **Format:** the header value is preceded with `sha256=`, i.e. `sha256=<hex>`.
- **Replay window:** not documented (silent — Meta relies on the signature plus server-side deduplication by message id). **Timing-safe:** not documented (silent) on this page.
- **Source / checked:** `developers.facebook.com/docs/messenger-platform/webhooks`; the same `X-Hub-Signature-256` contract is restated in the Graph API "Securing Requests" / webhooks getting-started references. Checked 2026-07-23.
- **Why `PARTIAL`:** the signature **mechanism** is fully attributable and documented — the `X-Hub-Signature-256` header, HMAC-SHA256 with the App Secret, the `sha256=` value format, the GET verify-token challenge and the escaped-unicode payload nuance. But the official page is **silent** on a replay/timestamp window and on timing-safe comparison; per the evidence contract, documentation silence is not `SPECIFIED`, so the row is `PARTIAL`.

## 4. Classification legend

- **`SPECIFIED`** — current official provider docs **affirmatively** establish every field the evidence contract requires: the header(s), the mechanism, exactly what bytes are signed, the timestamp/replay window (or an explicit statement that none applies), and whether comparison must be timing-safe — sufficient to implement correct verification with no field left to inference. Documentation **silence** on any required field is **not** `SPECIFIED`.
- **`PARTIAL`** — attributable to current official docs, but at least one required field is left **silent**, ambiguous, or internally inconsistent (e.g. the signed-byte canonicalization is undefined, the replay/timestamp window or timing-safe requirement is not documented, or the documented method contradicts Plexco's implementation specs), so a receiver cannot rely on the docs alone for that aspect. The gap is documented, never filled by inference.
- **`UNRESOLVED`** — no attributable current official source, or the contract can only be guessed/inferred → fail closed. A row in this state forces `HALT-EVIDENCE_INCOMPLETE` for the whole document (no overall result, no closure marker).

## 5. Boundaries & re-verification

- **Inbound ≠ outbound (AP-22).** This matrix covers only how Plexco verifies webhooks providers send **to** Plexco. It says nothing about outbound fixed-egress source IPs, allowlists or provider IP ranges (AP-22 / `deployment-infra.md`); the two directions must never be conflated to close a row.
- **No secret values.** Only header names, algorithms, formats and secret **roles** are recorded. Rotating, storing and KMS-encrypting the actual secrets is governed by `feature_connector_onboarding_tech.md` / `feature_zalo_channel_tech.md` / `feature_player_messenger_tech.md` and BL-SEC-1, not here.
- **Re-verification.** Provider docs change. Re-open a row and re-check its cited official URL before relying on it for implementation; treat a materially changed provider contract as invalidating that row's `Checked` date.
- **Evidence, not enablement.** The `WEBHOOK_AUTH_EVIDENCE_CLOSED` marker attests that all four inbound contracts are attributably documented — it is not `PLAN_READY`, `CODE_READY` or an authorization to build any inbound-webhook adapter, which remain P0/manual.
