## Document Convention

- **Product/UX spec** (`FE/feature_{name}.md`) — 7 sections: Mô tả, Use Cases + Edge Cases, Screens & States, Domain Model, Analytics Events, Acceptance Criteria, Open Questions / Changelog.
- **Backend Tech spec** (`BE/feature_{name}_tech.md`) — 6 sections: Tổng quan triển khai, Database Schema + Edge Cases (BE), API Contract, Chi tiết triển khai, Testing Plan, Rollout Plan + Changelog.
- **Entry points (bắt buộc mọi spec)** — subsection `### Entry points` trong §1 (`Mô tả` FE / `Tổng quan triển khai` BE), đặt trước `### Bất biến`. **Không** phải section top-level thứ 8 — là subsection của §1, nên count 7/6 section ở trên không đổi. FE dùng bảng `Entry | Route / Surface | Actor | Mô tả`; BE dùng `Entry | Caller | Mô tả`. Liệt kê đủ mọi surface: route, tab, deep link, bot command, notification, chat link, projector/job. Cả 2 template cấp section này (thêm 2026-08-14); spec mới thiếu nó không đạt review gate.
- **Use Case table — cột `Để… (benefit)` bắt buộc (thêm 2026-08-14).** UC table FE dùng 5 cột `ID | Actor | Hành động | Để… (benefit) | Kết quả`, đọc thành "Là {Actor}, tôi muốn {Hành động} **để** {benefit}". Cột này để reviewer challenge được "UC này có cần không?"; benefit chỉ lặp lại Hành động = UC thiếu lý do, không phải thiếu chữ. Bắt buộc cho spec mới; spec `Reviewed` hiện có bổ sung khi được sửa lần kế (cùng cơ chế uplift v2.33) — **không** sửa hồi tố. Là cột trong §2 nên count 7 section không đổi.
- **§6 subsection `### NFR compliance` bắt buộc (thêm 2026-08-14).** Bảng `NFR ref | Áp vào đâu trong feature này | Cách chứng minh` **trỏ ngược** catalog đã có: `../product/BRD.md` §8 (NFR-S / NFR-P / NFR-PF / NFR-R) và bảng `NFR-1..N` của `../product/TDD.md` (có cột Metric). **Không** định nghĩa NFR mới trong feature spec và **không** tạo file NFR song song — gap cần đóng là chiều spec → catalog, không phải thiếu catalog. Feature không chạm NFR nào → ghi `none` + lý do, không để bảng rỗng (rỗng không phân biệt "đã xét, không áp" với "chưa xét"). Là subsection của §6 nên count 7 section không đổi.

- Language: Vietnamese numbered headers (`## 1. Mô tả`, `## 2. Use Cases + Edge Cases`, ...).

## Review gates

Với spec mới hoặc spec được promote sang **Reviewed**, review gate kỳ vọng format Vietnamese-numbered và coverage tương đương: ≥10 use cases, ≥12 edge cases (Product) hoặc ≥12 edge cases + ≥20 test cases (BE). Legacy Reviewed spec được chấp nhận khi coverage tương đương đã thể hiện rõ, không cần đổi status chỉ vì cách đếm khác. Trước mỗi phase:

1. Resolve or explicitly defer open decisions affecting that feature.
2. Review Product and Backend specs together.
3. Verify cross-references against current BRD/PRD/TDD/business rules.
