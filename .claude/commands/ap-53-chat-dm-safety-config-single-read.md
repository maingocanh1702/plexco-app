# AP-53 — chat-dm-safety-config-single-read: collapse assert_dm_allowed's four config reads into one

Discharge DD-102's hard condition. `assert_dm_allowed()` in `0030` reads `chat_dm_safety_config` through
**four separate statements** (three inline `SELECT … WHERE singleton` + `dm_safety_enabled()`), each its
own READ COMMITTED snapshot, so a concurrent config tightening can apply partially to an in-flight call.
This slice recreates the function to read the singleton row **once**, before slice 7/8 become its first
callers. Behavior is byte-identical otherwise.

## The four things that are easy to get subtly wrong

**Do not weaken fail-closed while collapsing the reads.** The single `SELECT * INTO v_cfg … WHERE
singleton` leaves `v_cfg` all-NULL when the row is missing. `dm_safety_flags_enabled(NULL,…)` must return
false (its own `COALESCE(…,false)`), and the limits must `COALESCE(…,0)` so `rate_limit_check` still
denies. If any missing-row or per-flag case starts ALLOWING, you have shipped fail-open on the gate —
HALT.

**Keep `dm_safety_enabled()`'s missing-row semantics exactly.** Recreate it with the **outer** COALESCE
over the singleton subquery (`SELECT COALESCE((SELECT dm_safety_flags_enabled(...) FROM … WHERE
singleton), false)`). The inner-only form returns NULL on an empty row set — a silent regression that
`dm_current_read_allowed()` (root, `0031`) would inherit. Row 12 of the acceptance matrix exists to catch
exactly this.

**Do not fold `chat_pair_blocked` into the config read.** It reads a different table (`chat_blocks`);
DD-102 is scoped to `chat_dm_safety_config`. Leave it as its own statement.

**Do not touch anything but the read count.** Same branch order, same deny reasons, same uniform
`'chat safety blocked'` text, same read-action rate-skip, same `RAISE LOG` audit line gated on
`audit_enabled`, same `SET client_min_messages = warning`. If you find yourself changing any of those,
stop — the slice's whole claim is "byte-identical except four reads become one".
